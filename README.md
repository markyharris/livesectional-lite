# LiveSectional Lite

> **Setting up from scratch?** Follow **HOWTO.md** — a step-by-step,
> newbie-proof install guide covering everything in this README plus the
> hard-won lessons (usernames, service paths, sudo permissions).

A minimal LED sectional map: **METARs only**, one LED per airport, driven
from a single bulk download instead of hundreds of API calls. It reuses
the `airports` layout file from the full LiveSectional project unchanged; 
`NULL` = unlit placeholder, `LGND` = legend LEDs).

## How Lite differs from the original LiveSectional

Lite is a ground-up rework of the original LiveSectional that keeps
exactly one job — current flight categories on the wall — and discards
the rest:

- **Scale:** about 1,000 lines in two files (`metar_lite.py`,
  `webapp.py`) vs. roughly 7,600 lines across a dozen scripts
  (separate fetch, display, wipes, admin, and utility programs).
- **Data:** one bulk METAR cache download every 5 minutes instead of
  per-station API queries. The `airports` layout file is shared with
  the original, unchanged.
- **Interface:** one admin page — status, settings, power buttons,
  and the map builder — instead of many configuration pages and
  editors. The LED count is simply the number of lines in `airports`;
  there is nothing else to dimension.
- **Failure behavior:** a failed fetch keeps the last good frame lit;
  the map never goes dark over a network hiccup. Without the LED
  library it runs as a console simulation, so it can be tested on any
  machine before it ever drives a strip.
- **Updates:** `git pull` and a service restart.

What the original has that Lite does not: TAF and MOS display modes
(with a rotary-switch input to select between data types), a heat-map
mode that lights airports by how often you've landed there, OLED/LCD
info displays, and web-based backup of the config, airports, and log
files. See "Deliberately left out" below for the rest of the omissions.

## How the data works

Every 5 minutes the app downloads the Aviation Weather Center cache file:

```
https://aviationweather.gov/data/cache/metars.cache.xml.gz
```

That's one gzip'd XML file containing **all** current METARs worldwide,
regenerated by AWC every minute. The app parses it, keeps the newest
report per station, and filters to the stations in `airports`. No API
keys, no per-station requests, no rate limits to hit. If a fetch or parse
fails, the error is logged and the map keeps showing the previous data —
it never blanks and never crashes.

Colors are the standard LiveSectional scheme:

| Category | Color |
|----------|-------|
| VFR  | green |
| MVFR | blue |
| IFR  | red |
| LIFR | magenta |
| No data / NULL | off |

If the XML has no `flight_category` for a station, it's computed from
visibility and ceiling (lowest BKN/OVC layer) using standard FAA
thresholds. The first four `LGND` LEDs show the category colors above;
the remaining legend LEDs show no-data (off), high wind (blink), and
lightning (white), mirroring the original map's legend row.

## The four settings

Edited on the web admin page, stored in `config.json`, picked up by the
display loop on its next cycle:

1. **Brightness** — 0–100% applied to every LED.
2. **Night mode** — between the configured start/end times (default
   22:00–06:00 local) brightness scales to the night level
   (`night_brightness`, default 25% of normal; set it to 0 and the map
   turns completely off overnight).
3. **High winds** — stations with wind or gust ≥ 15 kt blink on a ~1 s
   cycle.
4. **Lightning** — stations reporting TS/LTNG flash white instead of
   showing a steady category color.

After each successful fetch, a single wipe sweeps the strip once
(~1.5 s) as LEDs switch to their new colors. There are no other wipes.

Running more than one map? The admin page also takes an optional
**map name**, shown in the page header and the browser tab so maps
stay easy to tell apart; the status box shows the Pi's hostname and
IP address. The status box also flags **"Update available"** when
the Pi's copy is behind the GitHub repository (checked hourly).

## Map builder

The admin page has a builder for setting up the `airports` file without
counting LEDs by hand. Pick a position (or step with Previous/Next) and
the display lights just that one LED, bright white at full brightness,
while the rest of the string stays dark - look at where it sits on the
map, type the station ID that belongs there, and Save. Stepping lights
each new position automatically; turn the builder light off to hand the
string back to the weather display.

Details:

- Positions are LED numbers, 0-based (LED 0 = line 1 of `airports`);
  the page also shows the line number and the entries on either side.
- Entries are station IDs as they appear in the METAR data (e.g.
  `KFLG`), or `NULL` for an unused position, `LGND` for a legend LED.
- Saving rewrites `airports` and takes effect on the map right away -
  the display loop reloads the file when it changes (and rebuilds the
  strip if the position count changed). No restart needed.
- The handoff is a small `builder.json` file written by the web app and
  read by the display loop; only the display process drives the strip.
- Already have a list? The builder section also uploads a whole
  `airports` file at once - the original LiveSectional's file is the
  same format, so a backup from one uploads as-is. The upload replaces
  the list (validated first; the previous list is kept as
  `airports.bak`) and takes effect the same way, no restart.

## Running

Two processes, both plain Python (stdlib + Flask; `rpi_ws281x` only on
the Pi):

```bash
# Display loop (run as root on the Pi - the WS281x library needs it)
sudo python3 metar_lite.py

# Web admin -> http://<pi-address>:5000/
python3 webapp.py
```

**There is no login on the web admin. LAN use only — do not expose it to
the internet.** The page also has a map on/off button: off darkens every
LED (legend included) while data keeps fetching, so turning it back on
is instant.

Off the Pi (no `rpi_ws281x` installed), `metar_lite.py` automatically
falls back to a console simulation that prints one line of category
letters per render (`V`/`M`/`I`/`L`, `*` = lightning flash, `.` = off,
`G` = legend):

```bash
python3 metar_lite.py --once   # one fetch + render, then exit
python3 metar_lite.py          # loop, printing continuously
```

Strip constants (GPIO 18, DMA 5, 800 kHz, WS2811 GRB) mirror
the existing LiveSectional `config.py` and sit at the top of
`metar_lite.py`.

## systemd units

`/etc/systemd/system/livesectional-lite.service`:

```ini
[Unit]
Description=LiveSectional Lite display
After=network-online.target
Wants=network-online.target

[Service]
WorkingDirectory=/home/pi/livesectional-lite
ExecStart=/usr/bin/python3 metar_lite.py
Restart=always
User=root

[Install]
WantedBy=multi-user.target
```

`/etc/systemd/system/livesectional-lite-web.service`:

```ini
[Unit]
Description=LiveSectional Lite web admin
After=network-online.target
Wants=network-online.target

[Service]
WorkingDirectory=/home/pi/livesectional-lite
ExecStart=/usr/bin/python3 webapp.py
Restart=always
User=pi

[Install]
WantedBy=multi-user.target
```

Enable with `sudo systemctl enable --now livesectional-lite livesectional-lite-web`.

**Power buttons:** the admin page's Reboot / Shutdown buttons run through
passwordless sudo scoped to a short command list (the web service itself
stays unprivileged). One-time setup — see HOWTO.md Step 7 for why every
entry is there, including `/bin/true` (the page's permission probe):

```bash
ME=$(whoami)
echo "$ME ALL=(root) NOPASSWD: /bin/true, /usr/bin/true, /sbin/reboot, /sbin/poweroff, /usr/sbin/reboot, /usr/sbin/poweroff, /bin/systemctl * livesectional-lite*, /usr/bin/systemctl * livesectional-lite*" | sudo tee /etc/sudoers.d/livesectional-lite-power
sudo chmod 440 /etc/sudoers.d/livesectional-lite-power
sudo visudo -c
```

(If the web unit runs as root instead, the buttons work with no setup.
Without the sudoers entry the page explains the setup when a power
button is pressed; nothing else is affected.)

## Deliberately left out

No TAF, no MOS, no other weather products. No selectable wipes (one
wipe, hard-coded). No per-station API calls. No accounts, no database,
no settings beyond the four above. If it isn't needed to light the map,
it isn't here.
